# HTTP/3 multiplexed per-request cost, 2026-10-21

#12887 slice 1: the HTTP/3 server's cost with many requests in flight on
one connection, the 1x256 nightly row where Fern trailed h2o. The
sequential path (`TestSelfHostServeAllocsPerRequestH3`) was already tight;
the copies and scans that remained were per request only when several
requests' work was applied in one pass, which is the multiplexed case
(`docs/NET-P8-HTTP3-PLAN.md` slice 10's "what remains").

## Method

A hello server under `with_tls().with_h3()` and a client holding m
requests in flight on one connection until n are answered
(`e2eharness.ServeAllocsH3ServerSource` and a multiplexed variant of its
client). Instructions are callgrind's count for the server over n =
40,000 at m = 64, on x86-64, a `-g` build. The server allows 100
concurrent request streams, so the client waits for a stream's credit to
return as responses are acknowledged. Allocations per request are
`__heap_alloc_count()` deltas the client reads off `/count`.

## The three costs, by the profile

At m = 64 the profile put a third of the server's instructions in
`streams.__find` scanning the stream list, and the HTTP/3 session scanned
and rebuilt its request list the same way; QPACK's encoder compared every
field against all 99 static entries.

- **The stream table** kept each bidirectional stream's position by
  sequence number in an index following the live window, so a lookup is
  O(1); the few unidirectional streams keep the end scan. `write` no
  longer copies the body twice when the sending half is empty.
- **The HTTP/3 session** does the same for its requests, and a finished
  request is marked gone and swept once half the list is, rather than the
  list rebuilt per request.
- **QPACK's static lookup** indexes the table's name groups by length, so
  a field's name is compared against the few entries of its length.

Both indexes are written only through the record that owns them, so the
reference counter updates them in place rather than copying.

## Result

| measure, m = 64, n = 40,000 | before | after |
|---|--:|--:|
| instructions per request | 50,329 | 42,612 |
| allocations per request | 139.2 | 133.7 |

The sequential count (m = 1) is unchanged at about 231, as expected: its
copies were already gone, and the ratchet
`TestSelfHostServeAllocsPerRequestH3` does not move. The in-memory
`http_h3q` suite gains a case, "the stream limit grants back as streams
close", covering the 100-stream boundary the multiplexed client reaches.

## How to rerun

Build the server and the multiplexed client from
`e2eharness.ServeAllocsH3ServerSource`, hold 64 requests in flight for
40,000 responses, and read the server under `valgrind --tool=callgrind`.
