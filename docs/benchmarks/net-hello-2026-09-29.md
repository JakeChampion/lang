# HTTP hello throughput, 2026-09-29

The first report of `scripts/net-bench`, the script `net-nightly.yml` runs
once a night on main (#9854). Two hello servers answering the same
five-byte body, loaded by oha 1.16.0 closed-loop at 64 and 4,096
connections: the Fern one (`scripts/net-bench.d/hello.fern`, built by the
Go compiler for x86-64, `tcp_serve_supervised_opts` with a worker per
core) and Go 1.27.1's net/http with its defaults
(`scripts/net-bench.d/gohello`). Loads of 3 s each on the 4-core
development container, generator and servers on the same cores, so the
figures are a ratio between the two servers on one box and not a
capacity; the nightly lane records 10 s loads on a GitHub runner, and
`scripts/perf-history show net/fern/c64.rps` reads that trend back.


Read `.rps` as requests per second, `.p50_us` and `.p99_us` as the median
and 99th-percentile latency in microseconds, `.failed` as responses that
were not 200 plus errors other than the requests the end of the run cut
off, and `held.bytes_per_connection` as the bump-allocator growth one
held connection costs the Fern loop (the number
`TestSelfHostHeldConnectionsHeapBoundX86_64` bounds at 1 KiB). The
connections it holds are accepted and never sent a request, so it is not
yet the exit criterion's idle keep-alive connection: one left open after a
served request costs over 10 KB today (#11204).

Since this reading the lane has gained the hyper and h2o columns the exit
criterion names, and the hello path's per-request instruction count is
perf.yml's (`examples/bench/http_hello.fern`).

## Accept distribution, 4,096 held over four workers

`TestSelfHostServeAcceptDistribution` dials 4,096 connections in a burst
from one client, one request on each, against
`tcp_serve_supervised_opts` with four workers over the shared listener
each watches with `EPOLLEXCLUSIVE`, and counts the connections per
worker (the handler answers a per-worker mark). Four runs of the Go
compiler's build and one of the self-host compiler's, on the same
4-core container, busiest worker first:

| build | connections per worker |
| --- | --- |
| Go compiler | 1811, 1365, 577, 343 |
| Go compiler | 1849, 1508, 461, 278 |
| Go compiler | 1966, 1512, 331, 287 |
| Go compiler | 1934, 1584, 488, 90 |
| self-host | 1210, 1095, 1091, 700 |

Every worker serves, and the spread is uneven under a burst: the worker
a wake-up reaches keeps accepting from a queue that never empties, so
the others wake less often. The shared listener stays the default on
that reading; per-worker `SO_REUSEPORT` listeners, which the kernel
balances, are the opt-in still to build (`docs/CRASH-ONLY-SERVE.md`).

## The hyper and h2o columns, the same evening

The two remaining servers #9854 names joined the table: hyper 1.11.1's
http1 server on a multi-threaded tokio runtime
(`scripts/net-bench.d/hyperhello`, one task per connection, built
`--locked`) and h2o 2.2.5 from Ubuntu's package, answering through an
mruby handler with a thread per core. Two-second loads on the same 4-core
container, the 64- and 4,096-connection points read from two runs, so
again a ratio on one box and not a capacity.
