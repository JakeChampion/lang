# HTTP/3 request allocation ratchet

The current compiler and crypto implementation on main use about 280.19
allocations per HTTP/3 hello request over one connection. Three independent
100,000-request samples agree:

| Sample | Allocations | Allocations per request |
| --- | ---: | ---: |
| CI on the ARM64 helper-fix branch | 28,019,249 | 280.19249 |
| Local integrated release-cleanup branch | 28,019,131 | 280.19131 |
| Local tightened gate with indexed manifest lookup | 28,019,208 | 280.19208 |

These are the counts reported by `TestSelfHostServeAllocsPerRequestH3`.
The gate requires tightening a ceiling when the reading is at least eight
allocations below it. Its former ceiling of 303 therefore fails on the
improved implementation. The ceiling is now 281, preserving less than one
allocation per request of headroom.

The CI sample is from run 39049489821. Local checks use release-cleanup
parent 5daa853c43039c73386c75a7098184179a63a21b; the second local run includes
the indexed manifest lookup and tightened ceiling. This records the
improvement already present in main's implementation.

## After h3q steps the QUIC connection in place

`h3q.Conn.__applied` took the QUIC connection out of its record, applied
the session's writes to it and stored it back, and every action went
through `conn.Conn.write`, whose `Result` keeps the connection alive for
the error path. Each of those copied the connection, its stream table
and every stream. `std/quic/conn` now has bare forms of its stream steps
(`written`, `read_into`, `stream_reset`, `sending_stopped`, with why one
did nothing in `refused`), and `h3q` steps the connection inside the
construction that stores it, as docs/REUSE-CONTRACT.md's known gaps
describe.

Instructions per request are callgrind's count for the arm64 Linux
`serve.run` hello server under h2load (ngtcp2), 20,000 requests after a
2,000-request warm-up, the warm-up's run subtracted, on main at
bbadbc3ff; repeated runs agree within 1%.

| measurement | before | after |
|---|--:|--:|
| instructions per request, 16 connections with 64 streams each | 77,105 | 61,675 |
| instructions per request, 64 connections with one stream each | 151,684 | 144,300 |
| allocations per request, sequential (`TestSelfHostServeAllocsPerRequestH3`) | 265.2 | 265.19 |

The sequential count does not move: with one request in flight the
copies were already gone after #12615. They remain wherever several
requests' writes are applied in one pass, which is the multiplexed case.
