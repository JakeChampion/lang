# Accepting a connection with accept4, 2026-11-07

The second half of #12887 slice 2. The nightly's HTTP/1.1 rows now report
the server's CPU for each request. The same-box check of 2026-10-21 put
the gap to h2o in kernel time. For each connection the loop made six
system calls before the first read. This change makes it four.

## Before

`scripts/net-bench.d/hello.fern` with one worker (`WORKERS=1`), under
`strace -f`, three connections from curl. The calls between the accept
and the first read, for each connection:

```text
accept(3, NULL, NULL)                        = 10
fcntl(10, F_GETFL)                           = 0x2
fcntl(10, F_SETFL, O_RDWR|O_NONBLOCK)        = 0
setsockopt(10, SOL_TCP, TCP_NODELAY, [1], 4) = 0
epoll_ctl(4, EPOLL_CTL_ADD, 10, ...)         = 0
getpeername(10, ...)                         = 0
```

The hello server lifts the connection cap for each address. With the
default `serve.config()`, which caps each address at 100 connections,
the loop also read the peer through `tcp_socket_ctl(sock, 7, 0)`: a
`getsockopt(SO_TYPE)` and a second `getpeername`, so eight calls.

## What changed

A new builtin, `tcp_accept_with(sock, nonblocking)`. On Linux and Android
it is one `accept4(2)` with `SOCK_CLOEXEC`, and `SOCK_NONBLOCK` when
asked. On Darwin, which has no `accept4`, it is `accept(2)` and then
`fcntl(2)` for the flags. On wasm it is the `tcp_accept` body with the
record's mode flag set from the argument. The Go interpreter sets the
connection's mode the same way.

`tcp_accept` stays as it was. The compiler's own interpreter calls it,
and the compiler's sources can call a builtin only when a published
stage0 knows it (`docs/BOOTSTRAP.md`).

`std/serve` and `std/metrics` accept with the new builtin and drop the
two `fcntl` calls. `std/serve` reads the peer address once, with
`net.peer_addr`, and keys the per-address connection count from that
address instead of a second read through `tcp_socket_ctl`. The key is
the one `net.peer_key` answers: an IPv4 address as one word, an IPv6
address by its first eight bytes.

## After

```text
accept4(3, NULL, NULL, SOCK_CLOEXEC|SOCK_NONBLOCK) = 10
getpeername(10, ...)                              = 0
setsockopt(10, SOL_TCP, TCP_NODELAY, [1], 4)      = 0
epoll_ctl(4, EPOLL_CTL_ADD, 10, ...)              = 0
```

Four calls for each connection, five with the default per-address cap.

## Measured on this box

A 4-core container, four workers, oha for 5 s at 64 connections, two
rounds in turn. The load generator shares the cores, so the ratio is the
reading, not the rate.

| round | mode | before, req/s | after, req/s |
|--:|---|--:|--:|
| 1 | a new connection for each request | 71,803 | 74,124 |
| 2 | a new connection for each request | 75,700 | 78,393 |
| 1 | keep-alive | 230,845 | 202,642 |
| 2 | keep-alive | 202,844 | 241,462 |

With a new connection for each request, the after build answers 3% more
requests in both rounds. With keep-alive the connections are few and the
two builds are within the run-to-run noise, as expected: the saving is
for each connection, not for each request. The nightly is the record.

## How to rerun

```
bin/fern -target x86-64-linux -o hello scripts/net-bench.d/hello.fern
WORKERS=1 PORT=18473 strace -f -e trace=network,fcntl,epoll_ctl ./hello &
curl -s http://127.0.0.1:18473/
```

`TestSocketCtlX86_64` and `TestSocketCtlArm64` run
`e2eharness.AcceptWithCloexecProbe`, which reads the accepted
descriptor's flags from `/proc/self/fdinfo`: close-on-exec on both
forms, non-blocking only when asked.
