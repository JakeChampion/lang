# HTTP/1.1 hello at 64 connections, 2026-11-10

On two nightly runs, `std/serve` (`net/fern`) is behind zap and hyper at 64
connections. It leads at 4,096 connections, and the io_uring server
(`net/fern-ring`) leads at 64. This note gives the measurements of the gap
and one change that it made.

## The nightly rows

The rows come from `refs/notes/perf` on the main commit of each run.

| run | server | c64 req/s | user µs per request | sys µs per request |
|---|---|--:|--:|--:|
| 2026-11-09, aafef0e89 | fern | 112,054 | 3.68 | 11.36 |
| | fern-ring | 114,433 | 3.76 | 10.64 |
| | hyper | 113,758 | 2.99 | 10.59 |
| | zap | 114,324 | 4.69 | 12.48 |
| 2026-11-10, e31c27c97 | fern | 110,273 | 4.03 | 11.52 |
| | fern-ring | 113,733 | 4.23 | 10.92 |
| | hyper | 111,856 | 2.91 | 10.67 |
| | zap | 111,351 | 4.63 | 12.68 |

Fern is 1.4% behind hyper and 1.0% behind zap on 2026-11-10. Each server
moved by about 2% between the two runs.

Zap uses more CPU for each request than Fern, and it serves more requests.
So the CPU time of each request does not set the limit by itself at this
connection count.

## No change of Fern's code between the two runs

The user time of `net/fern` rose from 3.68 to 4.03 µs. To find whether
Fern's code caused it, `scripts/net-bench.d/hello.fern` was built with the
compiler and the stdlib of each commit. Each server ran under callgrind with
`WORKERS=1`. `oha` sent 20,000 requests, then 40,000, on 64 connections.

| commit | instructions in the worker |
|---|--:|
| aafef0e89 | 522,453,209 |
| e31c27c97 | 522,810,596 |

The difference is 0.07%. The rise in user time is noise of the runner, not
a change of Fern's code.

## System calls

`strace -f -c` on the worker, for 50,000 requests on 64 connections:

| call | count |
|---|--:|
| `read` | 50,072 |
| `sendto` | 50,001 |
| `epoll_pwait` | 840 |

Each request costs one `read` and one `sendto`. No `read` fails with
`EAGAIN`, and one `epoll_pwait` serves about 60 requests. The loop makes no
system call that it can remove.

## Where the instructions go

The worker runs about 8,700 instructions for each request. These are the
largest functions, from a `-g` build at e31c27c97:

| instructions per request | function |
|--:|---|
| 2,867 | `http.parse_request_framed_from` |
| 510 | `serve.__serve_burst` |
| 467 | `http.__shared_string` |
| 264 | `serve.__serve_respond` |
| 224 | `serve.__serve_loop` |
| 218 | `serve.__serve_read_plain` |
| 215 | `__fern_buf_push` |
| 145 | `__fern_monotonic_ns` |
| 138 | `metrics.Histogram.observe` |
| 126 | `HeaderMap.get` |

In the parser, the most expensive line is `__bytes_are`, at 655
instructions for each request. The parser compares each header name and
value with the previous request on the connection, so that it can keep the
previous string. `__bytes_are` calls the `__mismatch_bytes_str` kernel.

## The change: the last bytes of a mismatch

On x86-64, the mismatch kernel compared 16 bytes at a time. When fewer than
16 bytes were left, it compared them one byte at a time, at 6 instructions
for each byte. A header value of 16 to 31 bytes therefore spent most of its
time in that loop. Arm64 already finishes with 8, 4 and 2 byte windows.

Now the kernel compares the last 16 bytes in one window, when the range is
16 bytes or longer. That window ends at the end of the range. It can
overlap bytes that already compared equal, so the first mismatch it finds
is the first mismatch of the range. `TestSelfHostMismatchIR` checks each
length from 0 to 40 with a mismatch at each position, for `__mismatch` and
`__mismatch_bytes_str`.

| worker, 60,000 requests | instructions |
|---|--:|
| main e23f590d1 | 522,806,840 |
| with the change | 518,061,356 |

That is 79 fewer instructions for each request, 0.91% of the worker.

## What is left

- `__bytes_are` still costs 576 instructions for each request. The parser
  calls it about seven times for each request, on short names and values.
  Most of each call is the setup of the kernel: five operands from the
  stack, and the clamp of both offsets and of the count. A kernel for
  equality of two ranges of the same known length needs none of that.
- `__scan_set_bytes` for the token characters (285) and for CR and LF
  (214), and `__memchr_bytes` for CR (195), scan the same bytes of the
  request line and the fields.
- `__fern_monotonic_ns` (145) and `metrics.Histogram.observe` (138) measure
  each request for the server's metrics.

## How to rerun

1. Build `scripts/net-bench.d/hello.fern` for `x86-64-linux`.
2. Start it under `valgrind --tool=callgrind` with `PORT` and `WORKERS=1`
   set.
3. Send 20,000 requests with `oha -n 20000 -c 64`, then 40,000.
4. Stop the server. The callgrind file of the forked worker is the larger
   one. Divide its total by the number of requests.
