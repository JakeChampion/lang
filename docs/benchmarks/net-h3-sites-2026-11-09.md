# HTTP/3 allocation sites per request, 2026-11-09

`TestSelfHostServeAllocsPerRequestH3` measures 50.69 allocations per
HTTP/3 hello request on main (f6e1e1d32). HTTP/1.1 measures zero. This
note gives the sites of those allocations, so that the next change of
`docs/NET-P8-HTTP3-PLAN.md` slice 10 can start from current numbers.

## Method

1. Write the gate's server and client with
   `e2eharness.ServeAllocsH3ServerSource(0, 2000)` and
   `e2eharness.ServeAllocsH3ClientSource`. Give the server a fixed port.
2. Build the server with `FERN_RC_TRACE=1 bin/fern -g -target
   x86-64-linux`, and the client without the trace.
3. Run the client for 2,000 requests. It also sends 2,000 warm-up
   requests first, so the trace covers 4,000 requests and the handshake.
4. Count the `rctrace a` lines by `site` and `caller`, and resolve both
   with `addr2line -f -e` on the server binary.

The trace gives 51.73 allocations per request. The 1.04 above the gate's
figure is the handshake and the warm-up, which the gate does not count.

## What the table shows

No site costs more than 3 allocations per request. Most cost one, because
each request makes one record or one list at that site. These are the
kinds:

- **A list that starts empty for each request.** The HTTP/3 session's
  events and the QUIC stream table's new-data list are emptied when the
  caller takes them, so the first append of each request allocates. Two
  lists that alternate, or a list that keeps its capacity, can remove
  them.
- **A record for each new stream.** A request is a new bidirectional
  stream, so `__new_stream`, its reassembly and the session's request
  record are made for each request. A free list of retired stream records
  can reuse them.
- **A buffer that a runtime kernel returns.** `packet.mask` gets a new
  16-byte block from `__fern_aes_ctr32` for each packet, in and out, and
  `packet.__slice` copies a range of the datagram. A kernel can write the
  mask as a scalar, or into a buffer it is given. That removes two
  allocations per request, and a view in place of the copy removes two
  more.

## Truncating a list in place, 2026-11-10

An event list can keep its buffer if the step that empties it calls
`truncate(0)` in place of `[]`. A list with one owner then keeps its
capacity. In a small program, 1,000 rounds of two appends cost 1
allocation with `truncate(0)` and 999 with `[]`.

The `events_taken` of `std/http/h3q` now does this. The gate measures
49.69 allocations per request in place of 50.69, and the multiplexed gate
28.69 in place of 28.82. The same change in the streams, the QUIC
connection and the HTTP/3 session gives the same figures, so those lists
stay as they are. Each of them has a second owner when its consumer
takes it, and a shared list that keeps nothing becomes the empty constant.

Compare both builds on one tree. On 2026-11-10 main measured 52.69,
because of a regression that this change ships beside its fix. A figure
from the day before was therefore not a valid baseline.

## How to rerun

The steps above. With the server at `$S/srv` and its trace at
`$S/trace.txt`, the counts come from:

```
grep '^rctrace a' trace.txt | awk '{print $5, $6}' | sort | uniq -c | sort -rn
```

Resolve each address with `addr2line -f -C -e srv 0x...`, and divide by
4,000.
