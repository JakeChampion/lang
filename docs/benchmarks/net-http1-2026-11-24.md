# HTTP/1.1 hello on the x86-64 nightly, November 18–24, 2026

Fern met both HTTP/1.1 targets on seven consecutive nights. At 64 connections, #12504 requires Fern's p99 latency to be at most 1.2 times H2O's. At 4,096 connections, #12505 requires Fern to serve at least as many requests per second as H2O. Each row compares the two servers within the same run. All four loads recorded zero failed requests each night.

The October investigation found that the load generator competing with the server for cores inflated tail latency. It also identified costs in the server itself. The accept queue now uses the host's backlog limit, and the loop tracks ready work and reuses connection slots. With 4,000 idle connections, those changes reduced server CPU for a connect/request/close cycle from 739–789 µs to 26 µs in the controlled comparison. The nightly measures the combined result on shared runners. [October measurements and fixes](net-connections-2026-10-17.md)

To reproduce the table, fetch `refs/notes/perf` and run `git notes --ref=perf show <head-sha>` for each linked run. In the `net/fern/` and `net/h2o/` rows, compare `c64.p99_us` and `c4096.rps` and check both connection counts' `.failed` rows. The HTTP benchmark job passed on every date. The November 21 and 24 workflows also reported failures in the separate TLS fuzz job.

A local x86-64 rerun of the repository’s connection-cost check on the November 24 main sources measured seven allocations per connect/request/close cycle both alone and with 3,000 idle connections. Server CPU was 0.0009 ticks per keep-alive request in both cases and 0.0020 versus 0.0021 ticks per connection cycle. The isolated Go harness used the repository’s `PerConnectionCostServerSource(0)` and `CheckPerConnectionCostFlat` with the native Fern compiler.
