# E030 — `match` is not exhaustive

A `match` on an enum doesn't cover every variant, and doesn't
have a wildcard `_` arm to catch the remaining cases. Fern
requires exhaustive matches so adding a new variant to an
enum surfaces every callsite that needs updating — silent
fall-through-to-default is a frequent source of bugs after
enum extensions.

## Example

```
enum Status { Ok, Err, Pending }

function describe(s: Status): string {
    match (s) {
        Ok => { return "ok"; },
        Err => { return "err"; },        // error[E030]: match is not exhaustive — variant Pending of enum Status is not covered (add an arm or use `_`)
    }
}
```

## Fix

Either cover the missing variant explicitly:

```
function describe(s: Status): string {
    match (s) {
        Ok => { return "ok"; },
        Err => { return "err"; },
        Pending => { return "pending"; },
    }
}
```

…or add a wildcard for the variants you don't care about:

```
function describe(s: Status): string {
    match (s) {
        Ok => { return "ok"; },
        _ => { return "not ok"; },
    }
}
```

## Why exhaustive

When `Status` later grows a new variant (`Cancelled`), every
non-wildcard match surfaces as E030 — the compiler tells you
exactly which call sites need an update. Wildcards opt out
of that protection; use them deliberately.

## Non-enum scrutinees

Match on integers / strings / other non-enum types always
needs a `_` arm regardless of whether you covered every
constant — the value space is infinite. E030 fires with the
"add an unguarded `_` arm" wording for those.
