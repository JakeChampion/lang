# P005 — Input nests too deeply

The parser is recursive descent: every level of nesting in the
source — a parenthesised expression, an array literal, a block,
a nested type, a tuple pattern — costs a frame of goroutine
stack. Past a fixed bound the parser stops and reports P005
instead of continuing until the stack is exhausted.

The bound is not a style limit. A stack overflow in Go is a
fatal runtime error: it cannot be recovered, so it would take
the whole process down — the compiler, the LSP serving your
editor, or the playground — with no diagnostic at all. P005 is
that same input arriving as an ordinary parse error.

## Examples

```
function f(): i32 {
    // error[P005]: input nests deeper than 5000 levels
    return ((((( /* … thousands more … */ 1 )))));
}
```

## Fix

Hand-written code does not reach this bound — the deepest
source in the Fern repository nests 183 levels, and the limit
is 5000. Hitting P005 nearly always means one of:

- **Unbalanced delimiters.** A missing `)` or `]` earlier in
  the file makes the parser treat everything after it as one
  ever-deeper expression. Check the position P005 reports, then
  look *above* it for the delimiter that was never closed.
- **Generated code.** A code generator emitting a deeply
  right-nested expression — a fold built as
  `f(a, f(b, f(c, …)))` rather than a loop — can reach it.
  Emit an iterative shape, or break the expression into
  statements that bind intermediate results.

## Why this shape

Each source nesting level costs more than one unit of the
parser's depth budget, because a single level descends through
several mutually recursive functions (expression, unary, type,
statement, pattern). So the reported limit is a budget of parse
recursion, not a count of `(` characters.

## See also

- P001 (unexpected token) — the error you get for an unbalanced
  delimiter that does *not* push the parser past the bound.
