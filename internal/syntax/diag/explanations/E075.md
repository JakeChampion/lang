# E075: `init` and the handler disagree about process-lifetime state

A handler-shaped program — one that defines `handle` and no `main` — gets
a `main` synthesised for it. When it also defines `init`, the two are
wired together as a two-phase lifecycle: build the state once at startup,
thread it through every request.

```fern
function init(plat: platform.Platform): (serve.Config, Map[string, i32]) {
    return (serve.Config { ...serve.config(), workers: 1 }, map_new(8));
}

function handle(hits: Map[string, i32], req: HttpRequest,
                plat: platform.Platform): (Map[string, i32], HttpResponse) {
    let n: i32 = hits.get_or(req.path, 0) + 1;
    return (hits.insert(req.path, n),
            http.ok(int.int_to_string(n)));
}
```

The synthesised `main` becomes
`serve.supervise_with(port, cfg, state, handle)` with the pair
`init` answered: each worker's loop owns the value, each request
receives it and returns the version the next one sees. `init` may take
nothing or the platform, and answer nothing, the state, the
`serve.Config` alone, or the config beside the state.

E075 is the two halves disagreeing, or an `init` nothing can call.

## `init` takes something other than the platform

```fern
function init(port: i32): i32 { return port; }                // E075
```

The synthesised `main` hands `init` the platform or nothing; anything
else has no caller. Read configuration through `plat.env` instead.

## `init` returns a value the handler does not take

```fern
function init(): i32 { return 7; }                        // E075

function handle(req: HttpRequest, plat: platform.Platform): HttpResponse {
    return http.ok("ok");
}
```

Nothing would carry the 7. Before this rule the value was built at
startup and dropped, which reads exactly like a warmed cache that
silently never warms. Either give `handle` the state parameter, or make
`init` return `void` — a `void` `init` still runs before the loop, which
is the right shape for logging a start line or reading an env var.

## The handler takes a state nothing produces

```fern
function handle(hits: i32, req: HttpRequest,
                plat: platform.Platform): (i32, HttpResponse) {    // E075
    return (hits + 1, http.ok("ok"));
}
```

There is no `init`, so there is no first value to thread. Add
`function init(): S` returning it, or drop the parameter.

## A stateful handler on `wasm32-wasi-http`

```fern
function handle(hits: i32, req: HttpRequest,
                plat: platform.Platform): (i32, HttpResponse) {    // E075 on wasm32-wasi-http
    return (hits + 1, http.ok("ok"));
}
```

The wasi:http proxy world starts a fresh instance for every request and
calls `handle(req, plat)` on it, so there is no loop to carry a state
from one request to the next, with or without an `init`. Build a
stateful handler for a native target; on `wasm32-wasi-http`, keep what
must outlive a request in a store the handler reaches through `plat`.

## Where the state lives

In the accept loop's own frame, which is what makes it process-lifetime:
Fern has no module-level mutable state. The one alternative — a
closure-captured `Cell[T]` — holds any cycle-free value, a table
included, but nothing that can carry a function or another cell (E057).

Two consequences worth knowing:

- The state is per worker. Every worker inherits the value `init` built,
  and a worker forked again after a death starts from that value, not
  from where the dead one left it; state that must outlive a crash
  belongs in a store the handler reaches through `plat`. Answer
  `workers: 1` in the config for one value across every request.
- The `wasm32-wasi-http` target refuses a state-taking handler outright.
  The proxy world's instance is per-request, so nothing there holds a
  value between calls.

## Writing your own `main`

This rule governs the synthesised `main` only. A program that writes its
own `main` pairs `init` and `handle` however it likes — including calling
neither.
