# E074: ambiguous method — two implementations of one name

A method name on a type may be provided by an inherent declaration or by
a trait the type implements. When more than one of those is available and
nothing separates them, `v.m()` is rejected rather than resolved to
whichever declaration the compiler happened to see first.

```fern
struct P { x: i32 }

trait Meters { function scale(self: Self): i32; }
trait Feet   { function scale(self: Self): i32; }

impl Meters for P { function scale(self: Self): i32 { return self.x; } }
impl Feet   for P { function scale(self: Self): i32 { return self.x * 3; } }

function main(): i32 {
    var p: P = P { x: 2 };
    return p.scale();       // E074: Meters or Feet?
}
```

## How a call picks between traits

Two traits providing one method name for one type is legal — it is only
the *call* that has to be unambiguous. A call ranks the candidates by
whether the calling module can name the trait without going through
somebody else's imports:

- a trait **declared in the calling module**, or one whose module the
  calling module **imports directly**, ranks first;
- everything else — a trait reachable only because some module you
  imported imported it — ranks second.

Exactly one candidate at the best occupied rank resolves the call. So a
trait of your own always beats one that merely arrived in the transitive
closure, and adding an import can never silently change which method a
working call runs: it can only turn a resolving call into this error.

The example above fails because both traits are declared right there, so
both rank first.

## What to write instead

Give one of them a different name. Trait methods are part of a published
contract, so the rename belongs on whichever trait is yours:

```fern
trait Meters { function to_meters(self: Self): i32; }
trait Feet   { function to_feet(self: Self): i32; }
```

If both traits are someone else's, the type does not have to implement
both — dropping one impl removes the ambiguity, and a wrapper struct can
carry the other:

```fern
struct PFeet { inner: P }
impl Feet for PFeet { function scale(self: Self): i32 { return self.inner.x * 3; } }
```

## Inherent versus trait

The same error fires when a type has both an inherent method and a
trait-provided one of the same name, and it fires at the *declaration*,
not at a call:

```fern
struct P { x: i32 }
trait Area { function area(self: Self): i32; }

impl Area for P { function area(self: Self): i32 { return self.x; } }
function (p: P) area(): i32 { return 0; }   // E074
```

The inherent method does not shadow the trait's. If it did, `p.area()`
would mean the trait method inside a generic body — where dispatch goes
through the `T: Area` bound — and the inherent method at a concrete call
site, which is one spelling with two meanings. Rename the inherent one.

## When this does not fire

- One provider. A type implementing a single trait that declares `m`, or
  carrying only an inherent `m`, is never ambiguous.
- Two providers where one outranks the other, per the ranking above.
- The same trait declared for the same type twice, or two inherent
  declarations of one name: those are plain redeclarations and report
  E006 (top-level redeclared) instead.
- A `dyn A + B` object whose two traits both declare `m`: that is
  E062 (ambiguous method on a multi-trait object), about the object
  rather than about the type.
