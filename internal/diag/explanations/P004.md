# P004 — At most one `_` placeholder in a piped call

A piped call `x |> f(a, _)` uses the topic placeholder `_` to
mark where the piped left-hand side substitutes, instead of
prepending it as the first argument. Only **one** `_` may appear
as a direct argument of the piped call — the parser rejects two
or more, because there is a single piped value and no way to
decide which hole it fills.

## Examples

```
function main(): i32 {
    // error[P004]: at most one `_` placeholder in a piped call
    5 |> add(_, _);
    return 0;
}
```

## Fix

Use a single `_` for the piped value and pass the other
arguments explicitly:

```
function main(): i32 {
    // 5 fills the one hole; the other argument is a literal.
    var r: i32 = 5 |> add(_, 3);   // add(5, 3)
    return r;
}
```

If you genuinely need the piped value in two positions, bind it
to a variable first and call the function directly:

```
function main(): i32 {
    var x: i32 = 5;
    var r: i32 = add(x, x);
    return r;
}
```

## Why

The pipe operator threads exactly one value — the left-hand
side — into the call on its right. A single `_` names where that
value lands; two `_`s would need two different values, so the
shape is ambiguous and rejected at parse time rather than
silently duplicating the argument.

Note that only a `_` that is a **direct** argument of the piped
call counts. A `_` nested inside a sub-expression is left alone
(it stays an ordinary identifier and fails the checker's E001
like any other unknown name), and a nested pipe consumes its own
`_`, so holes compose: `x |> f(y |> g(_), _)` resolves the inner
hole to `y` and the outer one to `x`.
