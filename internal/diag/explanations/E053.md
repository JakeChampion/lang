# E053 — `fip` / `fbip` function violates its shape rules

A function annotated `fip` (fully-in-place) carries a *checked guarantee*
that it performs no heap allocation — Koka's fully-in-place discipline.
The checker verifies this as a sound, conservative subset: anything it
cannot prove allocation-free is rejected. `fip` is verify-don't-enable —
the in-place lowering (constructor reuse, the copy-on-write unique-in-place
branch, tail-recursion-modulo-cons) already happens automatically; the
annotation only asserts and checks the result, so a hot path or an
in-place algorithm can guarantee it never touches the heap.

`fbip` (fully in place *with borrowing*) is the weaker sibling: the same
shape rules apply, except constructor expressions (struct / tuple
literals, payload-carrying enum variants) are allowed — the IR layer then
verifies each such site is reuse-paired with a dead uniquely-owned donor,
rejecting un-paired ones with **E068** at compile time. The graded forms
`fip(n)` / `fbip(n)` likewise admit constructors at this layer and let
the IR count them against the allowance `n`.

## What is allowed

- scalars, arithmetic / comparison / logical / bitwise operators;
- field and index **reads**;
- control flow (`if` / `while` / `for` / `match` / `return`);
- (re)binding local variables;
- in-place index writes to an **`own`** array parameter — the array is
  uniquely owned, so the write mutates in place rather than copying;
- calls to other `fip` functions and the whitelisted non-allocating
  builtins (`len`). An `fbip` function may also call `fbip` functions
  (a `fip` function may not — `fip` is the stronger claim);
- (`fbip` / graded only) struct / tuple literals and payload-carrying
  enum constructors — each verified reuse-paired or within the
  allowance by the IR layer (E068).

## What is rejected

- array literals (no array reuse pairing exists);
- (bare `fip` only) tuple / struct literals and payload-carrying enum
  constructors (each allocates a box);
- string concatenation (`a + b`) and string interpolation;
- writing through a **non-`own`** array (rc may be > 1, so the write
  copies-on-write);
- calling a function outside the fip/fbip family or making an
  indirect/closure call (the callee may allocate);
- combining the modifiers: a function is `fip` or `fbip`, not both.

## Example

```
// error[E053]: `fip` function "scale" may not allocate (array literal)
fip function scale(own xs: i32[]): i32[] {
    return [xs[0] * 2];          // allocates a fresh array
}

// OK: mutates the uniquely-owned array in place, allocates nothing.
fip function double_first(own xs: i32[]): i32[] {
    xs[0] = xs[0] * 2;
    return xs;
}

// OK as fbip: the consuming match hands each Cons box straight to the
// arm's rebuilt Cons — on unique input the function allocates nothing.
enum List { Cons(i32, List), Nil }
fbip function map_inc(own xs: List): List {
    match (xs) {
        Cons(h, t) => { return Cons(h + 1, map_inc(t)); },
        Nil => { return Nil; },
    }
}
```

## Fixing it

Either remove the annotation (the function is still compiled with all
the same in-place optimizations — `fip`/`fbip` only *check* the
guarantee), weaken it (`fip` → `fbip`, or grade it `fip(n)` / `fbip(n)`
to permit n fresh constructions), or rewrite the body to mutate an
`own` argument in place instead of constructing new values.
