# E053 — `fip` / `fbip` function violates its shape rules

A function annotated `fip` (fully-in-place) carries a *checked guarantee*
that it performs no heap allocation at all. The checker verifies this as
a sound, conservative subset: anything it cannot prove allocation-free is
rejected. `fip` is verify-don't-enable — the in-place lowering
(constructor reuse, the copy-on-write unique-in-place branch,
tail-recursion-modulo-cons) already happens automatically; the annotation
only asserts and checks the result, so a hot path or an in-place
algorithm can guarantee it never touches the heap.

Constructor expressions — struct / tuple literals and payload-carrying
enum variants — are admitted in **every** tier, `fip` included. The
checker cannot tell a rebuild that reuses a dead donor's box from one
that allocates a fresh box, so it does not try: the IR layer verifies
each site is reuse-paired and rejects the un-paired ones with **E068**.
Bare `fip` is the allowance-0 case of that rule, and the graded forms
`fip(n)` / `fbip(n)` let the IR count un-paired sites against `n`.

`fbip` remains the weaker sibling on the axis that is left: an `fbip`
function may call `fbip` functions, where a `fip` function may call only
`fip` ones.

**Coming from Koka, note the tiers split on a different axis.** There
`fip` admits a constructor paired against a reuse credit and `fbip` adds
*borrowing* — non-consumed parameters. Fern borrows parameters by default
and marks consumption with `own`, so that axis has no keyword to hang on;
the pair here splits on what a body may CALL instead. On the constructor
rule Fern's `fip` now matches Koka's, which is what makes
`fip iteration(own state) -> state` expressible over a struct; rejecting
the rebuild syntactically used to leave `fip` unable to carry struct
state at all, since the field write E048 refuses names the rebuild as its
remedy.

## What is allowed

- scalars, arithmetic / comparison / logical / bitwise operators;
- field and index **reads**;
- control flow (`if` / `while` / `for` / `match` / `return`);
- (re)binding local variables;
- in-place index writes to an **`own`** array parameter — the array is
  uniquely owned, so the write mutates in place rather than copying;
- `xs.map(f)` on an **`own`** array — the in-place map (R7 in
  `docs/REUSE-CONTRACT.md`). Whether the result is written through the
  donor depends on the call — the receiver must be the consumed
  parameter itself and `f` capture-free and effect-free — so the
  checker admits the shape and the IR layer verifies it (E068), naming
  the rule when it declines. `f` is inside the claim: what it calls
  must be `fip`;
- calls to other `fip` functions and the whitelisted non-allocating
  builtins (`len`). An `fbip` function may also call `fbip` functions
  (a `fip` function may not — `fip` is the stronger claim);
- struct / tuple literals and payload-carrying enum constructors, in
  every tier — each verified reuse-paired, or within the graded
  allowance, by the IR layer (E068).

## What is rejected

- array literals (no array reuse pairing exists);
- string concatenation (`a + b`) and string interpolation;
- writing through a **non-`own`** array (rc may be > 1, so the write
  copies-on-write);
- calling a function outside the fip/fbip family or making an
  indirect/closure call (the callee may allocate);
- combining the modifiers: a function is `fip` or `fbip`, not both.

## Example

```
// error[E053]: `fip` function "scale" may not allocate (array literal)
fip function scale(own xs: i32[]): i32[] {
    return [xs[0] * 2];          // allocates a fresh array
}

// OK: rewrites one slot of the uniquely-owned array. `.with` is the
// spelling a subscript assignment is refused in favour of (E056), and on
// a unique input it writes the block in place rather than copying it, so
// the function allocates nothing.
fip function double_first(own xs: i32[]): i32[] {
    return xs.with(0, xs[0] * 2);
}

// OK: the same-shape map writes through the donated buffer (R7), so the
// function allocates nothing. The IR layer checks that it did: a
// capturing element function, or a map to a different element type, is
// an E068 naming the rule.
import "std/array";
fip function dbl(x: i64): i64 { return x * (2 as i64); }
fip function twice(own xs: i64[]): i64[] {
    return xs.map((x: i64): i64 => dbl(x));
}

// OK: the rebuild reuses the box `s` is handed in, so `fip` allocates
// nothing. A field write here would be E048, whose remedy is this line.
struct State { count: i32 }
fip function bump(own s: State): State {
    return State { ...s, count: s.count + 1 };
}

// OK as fbip: the consuming match hands each Cons box straight to the
// arm's rebuilt Cons — on unique input the function allocates nothing.
enum List { Cons(i32, List), Nil }
fbip function map_inc(own xs: List): List {
    match (xs) {
        Cons(h, t) => { return Cons(h + 1, map_inc(t)); },
        Nil => { return Nil; },
    }
}
```

## Fixing it

Either remove the annotation (the function is still compiled with all
the same in-place optimizations — `fip`/`fbip` only *check* the
guarantee), weaken it (`fip` → `fbip`, or grade it `fip(n)` / `fbip(n)`
to permit n fresh constructions), or rewrite the body to rebuild from an
`own` argument — `T { ...old, f: v }` — so the construction has a donor
box to reuse instead of allocating a fresh one.
