# E068 — `fip` / `fbip` function fails IR allocation verification

A function annotated `fip` / `fbip` (optionally graded, `fip(n)` /
`fbip(n)`) carries a *checked* fully-in-place guarantee. Two layers
enforce it:

- **E053** (the checker) enforces the *shape* rules — what constructs
  may appear in the body at all.
- **E068** (this error, the IR layer) verifies the code the compiler
  *actually emitted* matches the claim: after lowering, every fresh
  heap-allocation site in the function is counted against the
  annotation's budget.

The budget:

- `fip` — zero **un-paired** allocation sites. E053 admits the
  constructor shape here just as it does for `fbip`, because the checker
  cannot tell a paired rebuild from a fresh one; this layer can, so a
  bare `fip` is simply the allowance-0 case of the rule below. A rebuild
  paired with a dead uniquely-owned donor passes; an un-paired one is
  an E068 error naming the construct and its position.
- `fbip` — every constructor site (struct / tuple literal,
  payload-carrying enum variant) must be **reuse-paired**: the Perceus
  reuse analysis hands it the box of a dead, uniquely-owned donor — the
  general pairing, a self-overwrite (`p = P { … }`), or a consuming
  `match` on an `own` enum parameter whose arm rebuilds a variant
  (the zero-alloc `map`-over-unique-list shape). An un-paired
  construction is an E068 error. `docs/REUSE-CONTRACT.md` names each
  pairing shape (R1–R4) and what taints one.
- `fip(n)` / `fbip(n)` — at most `n` fresh (un-paired) allocation sites
  are permitted.
- A `std/array` **`map`** the checker admitted on an `own` receiver
  (E053) is a site too. It is allocation-free exactly when R7 of
  `docs/REUSE-CONTRACT.md` writes it through the donor: the receiver is
  the consumed parameter itself, the element function is a plain
  function (no captures) that reaches no observable effect, and the
  element type is unchanged. A `map` that misses one of those is
  counted as fresh, and the message names which — the same verdict
  `fern -array-report` prints for the stage. A closure that captures
  nothing is a plain function value and is not a site.

On the **self-hosted** compiler there is no in-place map yet, so every
`map` in an annotated function is counted as fresh, with a message saying
so: the annotation is refused there rather than accepted unchecked.

## The runtime `is_unique` fallback does not count

fip/fbip is a **shape** guarantee, exactly as in Koka: a reuse-paired
site still checks `is_unique(donor)` at runtime, and when the input is
*shared* it falls back to a fresh allocation (the donor's alias keeps
its box). That fallback branch is part of the paired form and never
counts against the budget — on unique inputs the function allocates
nothing; on shared inputs it may copy.

## Where the error is reported

The verification runs when the function is *lowered* (any compiled
target: x86-64, arm64, wasm). `fern -check` and the interpreter stop at
the E053 shape layer, so an E068 surfaces at compile time. It also only
runs under the default memory-management configuration — the debug
flags that force the reuse/free layers off disable the verification
along with the machinery it verifies.

## Example

```
struct P { x: i32, y: i32 }

// error[E068]: `fbip` function "mk" allocates: 1 un-reused allocation
// site(s) exceed the allowance of 0
fbip function mk(a: i32): P {
    return P { x: a, y: a + 1 };   // fresh box, no dead donor to reuse
}

// OK: the construction is paired with the dead `a` — it reuses a's box.
fbip function churn(a0: i32): i32 {
    var a: P = P { x: a0, y: a0 + 1 };   // needs fbip(1): the first box is fresh
    var s: i32 = a.x + a.y;              // a's last use
    var b: P = P { x: s + 1, y: a0 };    // paired: takes over a's box
    return b.x + b.y;
}
```

`churn` above still has ONE fresh site (the initial `a`), so it
verifies as `fbip(1)` — grade the claim when a bounded number of fresh
constructions is intended:

```
fbip(1) function churn(a0: i32): i32 { … }
```

## Fixing it

- Restructure so each construction can take over a dead, uniquely-owned
  value of the same shape (consume an `own` parameter in a `match` and
  rebuild, or overwrite a local after its last read) — see
  `docs/REUSE-CONTRACT.md` for the exact patterns and what taints them.
- For a `map`: hand it the `own` array parameter directly, give it an
  element function that captures nothing and calls only `fip`
  functions, and keep the element type.
- Grade the claim: `fbip(n)` / `fip(n)` permits `n` fresh sites.
- Or drop the annotation — the reuse optimization itself is unchanged;
  the annotation only asserts and checks it.
