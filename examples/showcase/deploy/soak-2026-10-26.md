# Sustained multiplayer check: 2026-10-26

The optimized x86-64 Linux server ran each workload for 180 seconds.
The source commit was `efa744441`. Node was version 24.19.0.
The CPU quota was four cores on an AMD EPYC 9V74 host.
The same workspace also ran TLS and deployment checks during this test.

Every participant used a real WebSocket connection. Every connection submitted inputs continuously.
One eighth of the clients ran in a separate process. Each run killed and replaced that process five times during measurement.
Other clients disconnected gracefully and reconnected. The tests confirmed seat recovery after every cycle.

| Workload | Participants | Graceful reconnects | RSS after warmup | RSS growth | Largest sampled p95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Foundry | 256 | 70 | 22.30 MiB | 0 MiB | 13.90 ms |
| Gather | 512 | 140 | 23.95–24.10 MiB | 0.15 MiB | 39.01 ms |
| Blockyard | 512 | 140 | 24.41–24.45 MiB | 0.05 MiB | 43.87 ms |

Each client process retains its most recent 8192 acknowledgement samples.
The table reports the largest sampled p95 window from the main client process.
It does not report a percentile over all inputs. Five-second samples can miss shorter events.
These loopback measurements exclude Internet distance and hosting limits.

All three workloads retained exactly 520 server descriptors at each sample.
Seat and descriptor counts returned to their idle bounds after the clients closed.
No snapshot, acknowledgement, cargo-conservation, RSS-growth, or descriptor guard failed.
The final crash cleanup also terminated the last client process.

## Durable deployment check

The local production image ran behind Caddy with certificate validation enabled.
Native JSON and static HTML responses decoded with the Node platform decoders for Brotli, gzip, and zstd.
The app recovered its database, archive, factory cargo, circuits, processor program, and sequence after SIGKILL.
The backup helper stopped the writer, created an archive, and restarted the app.
A new empty volume restored the same checkpoints successfully.

This check covers container death and replacement. It does not simulate a host disk failure or prove indefinite memory stability.
The public Netlify deployment still uses temporary storage. Public durable deployment requires a configured host and domain.

## Reproduce

Build the server and image through the instructions in [README.md](README.md).
Run the deployment regression and sustained tests from the repository root:

```sh
FERN_SHOWCASE_IMAGE=fern-showcase:latest node examples/showcase/tests/deployment.mjs
node examples/showcase/tests/soak.mjs http://localhost:8080 foundry 180
node examples/showcase/tests/soak.mjs http://localhost:8080 gather 180
node examples/showcase/tests/soak.mjs http://localhost:8080 blockyard 180
```

Use a dedicated server with no visitors. Set `FERN_SOAK_PID` to its PID for the descriptor check.
The client must run in the same Linux PID namespace as the server for that measurement.
The optional **Showcase endurance** workflow repeats the tests through TLS and retains the logs as artifacts.
