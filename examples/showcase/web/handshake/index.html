18Quantum-safe key agreement

Post-quantum handshake.

Agree on a secret key with the server, safe against a future quantum computer. Fern runs your half in this page as WebAssembly and the server half natively.

Load the Fern kernel

  1. Make key pairs in your browser

    Fern Wasm

    An ML-KEM-768 key pair and an X25519 key pair, from 96 random bytes that your browser supplies.

  2. Send the public keys

    HTTPS

    Only public values travel: the 1,184-byte encapsulation key and the 32-byte X25519 key.

  3. The server encapsulates a secret

    Native Fern

    The server answers with a 1,088-byte ciphertext, its X25519 key, a confirmation, and a sealed message.

  4. Derive the same key in your browser

    Fern Wasm

    Your browser opens the ciphertext and combines both shared secrets with the transcript of every public value.

  5. Confirm the server and read its message

    Fern Wasm

    The server's HMAC must match, and only the shared key can open the ChaCha20-Poly1305 message.

How it works

ML-KEM-768 is the post-quantum key encapsulation standard (FIPS 203). X25519 is the classical exchange most connections use today. The session key depends on both, as in the X25519MLKEM768 hybrid that TLS uses, so an attacker must break both. Neither side sends a secret. A change to any public value changes the transcript, so the confirmation fails. Your browser supplies the random seed. The Wasm kernel itself has no random source.
